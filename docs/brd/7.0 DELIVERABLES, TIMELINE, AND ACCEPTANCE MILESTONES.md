# 7.0 DELIVERABLES, TIMELINE, AND ACCEPTANCE MILESTONES

## 7.1 Purpose

This section defines the expected deliverables, milestone schedule, and acceptance checkpoints for the Living With Lolo (LWL) Consolidated Client Communications Hub Implementation. It ensures clarity on scope, sequencing, review processes, and completion criteria for internal implementation.

This timeline reflects Phase 1: Client Communications Hub—focused exclusively on client-facing email, SMS, internal notes, and centralized communication visibility. This phase explicitly excludes voice call and voicemail integration. Subsequent vendor communication capabilities will be addressed in future project phases.

## 7.2 Project Phases Overview

| **Phase** | **Objective** | **Key Deliverables** | **Duration Estimate** |
|-----------|--------------|---------------------|---------------------|
| Phase 1: Discovery & Planning | Validate requirements, confirm data sources, define project IDs, and establish integration scope. | Discovery summary, configuration blueprint, integration plan, data mapping schema. | 3 weeks |
| Phase 2: System Configuration & Setup | Build and configure HubSpot workspace, connect Gmail, and establish communication routing logic. | Configured HubSpot instance, routing workflows, unified inbox setup, sample test data. | 4 weeks |
| Phase 3: Integration & Testing | Connect SMS platform enable SMS perform QA testing. | Active integrations, test scripts, functional QA checklist, issue log. | 3 weeks |
| Phase 4: User Acceptance Testing (UAT) | Validate system functionality against this BRD; ensure all channels, routing, and dashboards operate as intended. | UAT plan, testing feedback log, resolution tracking, sign-off document. | 3 weeks |
| Phase 5: Training & Deployment | Prepare and conduct user training, transition to live production, and ensure documentation handoff. | User guides, admin training, final system documentation, go-live checklist. | 2 weeks |
| Phase 6: Stabilization & Handover | Monitor live system for 2 weeks post-launch, resolve defects, and confirm full acceptance. | Issue log closure report, final acceptance sign-off, future recommendations. | 2 weeks |

Total estimated duration: 17 weeks, subject to discovery validation.

#### 7.3.1.7 External Integration Architecture

**PREREQUISITE:** LWL's Airtable Administrator has completed webhook proof-of-concept demonstrating successful Airtable-to-Zapier communication (see Section 1.6.3.3).

**Integration Ownership Model:**

- Airtable webhook automations: Built and maintained by LWL's Airtable Administrator
- Zapier workflows: Built and maintained by LWL's Airtable Administrator
- HubSpot API endpoints: Configured by LWL IT Lead
- HubSpot POC assignment workflows: Built and maintained by LWL IT Lead
- Field mapping documentation: Collaborative (both parties)
- Ongoing sync monitoring: LWL's Airtable Administrator with 90-day escalation support from LWL IT Lead
- POC assignment workflow monitoring: LWL IT Lead

The solution requires event-driven one-way data synchronization from Airtable (authoritative source for project metadata) to HubSpot using Airtable automations, webhooks, and Zapier as the middleware platform.

**Required synchronization fields:**

- Project ID (unique identifier)
- Client contact information (all available email addresses and phone numbers with descriptive labels)
- Project phase status

**Event-Driven Synchronization Strategy:**

**Trigger 1: New Paid Project Sync**

When a project's status changes to "Paid" in Airtable:

1. Airtable automation detects status change
2. Automation triggers webhook to Zapier with Project ID, client contact information, and **current phase**
3. Zapier receives webhook and creates new Deal record in HubSpot
4. Deal includes: Project ID, client contact info, phase property
5. **HubSpot workflow automatically triggers on "New Deal Created"**
6. **Workflow reads phase value (e.g., "PreDesign") and automatically assigns:**
   - Primary POC (e.g., Molly for PreDesign phase)
   - Backup POC (e.g., Robin for PreDesign phase)
   - Based on phase-to-POC mapping logic defined in Appendix C

**Trigger 2: Phase Change Sync**

When a project's "Phase" field changes in Airtable:

1. Airtable automation detects phase field change
2. Automation triggers webhook to Zapier with Project ID and updated phase value
3. Zapier receives webhook and updates existing Deal record's phase property in HubSpot
4. **HubSpot workflow automatically triggers on "Phase property changed"**
5. **Workflow reads new phase value (e.g., "Design") and automatically updates:**
   - Primary POC (e.g., Sara for Design phase)
   - Backup POC (e.g., Meghan for Design phase)
   - Based on phase-to-POC mapping logic defined in Appendix C
6. **Note:** Active conversations retain their current POC assignment (conversation ownership persistence per Section 3.3.7); only NEW conversations route to updated POCs

**Safety Net: Weekly Baseline Sync**

Every Sunday at 6:00 AM Arizona Time:

- Zapier scheduled workflow fetches all Paid projects from Airtable
- Workflow updates or creates corresponding Deal records in HubSpot
- Updates project metadata (Project ID, contacts, phase)
- **HubSpot POC assignment workflow automatically triggers** for any phase changes detected
- Catches: Manual contact info updates, missed webhooks, data drift corrections
- After 90 days of stable operation, LWL may discontinue weekly baseline sync if event-driven triggers prove 100% reliable

**Error Handling:**

- Automatic retry logic: Up to 3 attempts for failed webhook deliveries
- Administrator notifications: Alert LWL IT Lead and Airtable Administrator for persistent failures
- **Phase name validation:** Airtable phase values must exactly match HubSpot workflow phase names (case-sensitive)
- **POC assignment workflow monitoring:** Weekly automated report identifies Deals with blank Primary POC (indicates workflow failure)
- Data validation: Verify all required fields populated before sync
- Manual override: Admins can manually trigger sync for individual projects via Zapier interface

**Implementation Approach:**

**LWL's Airtable Administrator (Josh) will:**

- Build Airtable automations to detect "Paid" status changes and "Phase" field changes
- Configure webhook actions in Airtable automations
- Provide Zapier webhook URLs to Airtable automations

**The LWL IT Lead will:**

  - Webhook payload structure expected by Zapier

  - Authentication and API connection requirements
  - Testing and validation procedures

IF Phase = "PreDesign" THEN
Set Primary POC = Molly
Set Backup POC = Robin

IF Phase = "Design" THEN
Set Primary POC = Sara
Set Backup POC = Meghan

IF Phase = "Procurement" THEN

Alert administrator

- Configure workflow triggers:

**Vacation Flag Routing:**

- Each HubSpot user has "Out of Office" boolean property
- When new conversation is assigned to a POC, HubSpot checks vacation flag:
  - If Primary POC "Out of Office" = TRUE → route to Backup POC
  - If Primary POC "Out of Office" = FALSE → route to Primary POC
- Vacation flag logic is independent of POC assignment workflow
- Users manage their own vacation flags; administrators can override
